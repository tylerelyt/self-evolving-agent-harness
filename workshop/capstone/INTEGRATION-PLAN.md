# 综合实战｜让多实例巡检共同改进值班 Skill

学员接手订单、支付、库存和通知四类本地服务。同一实验中，两个 Hermes Agent 同时巡检各自负责的范围。实验环境模拟外部监控服务，注入故障并发出带事故 ID 的告警。Harness 通过原生 steer 把这条告警交给正在运行的 Agent，Agent 读取当前正式 Skill 并调查。两个 Agent 将完成的值班会话归档到同一 SkillClaw 共享组。Evolve Server 汇集这些经历，提出一份共享 Skill 候选。候选通过业务验收才发布给两个 Agent，由各自的新任务读回并产生下一轮经历。

双实例入口组合实时巡检、分支补查、审批处置、原生会话归档、候选演化、业务回放和双端同步读回。演练结束后按事故导出 HTTP 工作样本，可用 Hermes 重新执行初判。本文说明各组件的职责、数据来源、可选集成与验收边界；独立练习见各讲目录，运行命令见[综合实战 README](README.md)。

## 两轮巡检和学习

双实例演练用持续和间歇 HTTP 503 验证两轮学习。Hermes 先初判，再从事故报告 Item fork 补查。值班工程师引用分支报告，签批清除本地故障，每个环境记录两个互不重叠的健康窗口。后台复盘和可选的 GEPA HTTP 对照分别保留来源与结果。下表列出演练的阶段与检查对象。

A、B 是同时运行的独立 Hermes 实例。最小演练可在一台机器上开两个进程，使用不同的实例 ID、Hermes Home、会话库和 SkillClaw Client Proxy。两个实例跑同一套巡检与调查逻辑，以东区和西区的教学环境作为各自的责任范围。实验从同一份正式 Skill 开始，保留相同的工具种类和权限规则，让不同经历来自各自遇到的故障。两个客户端指向同一个本地 SkillClaw 共享组，该组运行一个 Evolve Server。

| 阶段 | 现场和任务 | 必须留下的结果 |
| --- | --- | --- |
| 起步 | A、B 同时巡检各自的环境，确认正常窗口与低样本窗口，并读取同一版种子 Skill | 两个实例 ID、各自的 Session 与 Item、相同的正式 Skill 哈希 |
| 第一轮调查 | 在两个范围内注入不同故障。例如 A 遇到同一事故导致的多服务告警，B 遇到容易混淆的并发事故或过时日志入口。各自走 steer、Skill 读取、现场取证和恢复确认 | A、B 各一份完成的调查会话，包含工具回执、事故范围和所读 Skill 版本 |
| 第一轮进化 | 两个 Client Proxy 把会话归档到同一个 SkillClaw 组。Evolve Server 运行 Summarize、Aggregate、Execute，提出共享候选或保留现行版本。Hermes 本地复盘更新事实、整理方法草稿，GEPA 离线生成对照候选 | 同一演化批次能追到 A、B 的源 Session，候选记录父版本与来源，另有 Memory 差异和数据集版本 |
| 评测与采用 | 用独立回放题比较现行版与候选。符合发布门槛后，SkillClaw 将正式版本同步给 A 和 B | 逐题结果、采用决定、两边的同步回执，以及两个新任务的实际加载哈希 |
| 第二轮调查与进化 | A、B 继续巡检并处理新的故障。用新会话验证新版在不同范围里的行为，再将两边的新证据送回 SkillClaw。演练一次拒绝或回退 | 新版本的实际调用与回执、第二批源会话、下一条改进假设、回退后的加载与复跑证据 |

第一轮可检验扩大查询范围是否能补全同一事故的受影响服务，以及按事故 ID 筛选是否能阻止误收同集群的其他事故。两条假设分别评分。第二轮用新事故和旧版成对回放，观察采纳后是否出现新的方法缺口。实验环境需要把故障开关、真实请求和可重放的告警、调用链、日志关联到同一个事故标识。单次 HTTP 503 证明该请求失败，进一步定位根因依靠独立的链路和日志回执。

## 事故处理与学习怎样相接

事故记录沿用原有巡检 Session、Turn 和 Item，加上实例 ID、事故 ID、服务和环境、异常窗口、steer 投递文本、调查 Session、Skill 内容哈希、工具回执、审批、执行结果及恢复观察。初判留在收到 steer 的巡检回合。长调查从同一事故的报告 Item fork，记录父会话、分支会话和事故 ID。Hermes 通过 `skill_view` 再读事故固定的 Skill 版本，在原环境依次取得三次新探测的回执，并将根因记录为未知。审批引用对应实例的 `collection/<实例>/investigation.json`。

Client Proxy 用显式 Session ID 关联初判请求。两个原始初判任务结束并完成归档后，按实例 ID 和 Session ID 纳入演化批次。归档就绪由会话文件与原始工具回执核对确认。分支会话的回执供调查和审批核对，避免同一事故的上下文重复进入本轮学习。共享事实通过 Memory Provider 提供按需检索，并保留版本与原始来源。

采用时锁定通过评测的候选哈希。SkillClaw 的原生验证记录与业务工具回放结果分别保留，发布前核对正式库即将采用的内容与通过业务评测的版本一致。在线巡检只同步正式版本，在途任务继续使用启动时固定的副本。

处置复用现有事故状态机。实验执行器接受绑定事故、范围和具体动作的批准，重复请求可追到同一执行回执。双实例演练已接入本地故障清除和两个独立的 HTTP 恢复窗口。单实例实作由学员控制故障开关，重启后的交班与继续追踪可在[值班学习实作](LEARNING-LAB.md)中单独演练。

每轮关闭事故后，编排器用已落盘的回执启动隔离的 Hermes Background Review。复盘写入只作为提案，编排器核对后才提交历史事实。下一轮接班用 Hermes `MemoryProvider` 的按需检索读取另一个实例的历史事实，并取得新的 HTTP 指标。将 `proposal.json`、`handoff.json` 与源 Session 和 Item 对照，可区分事实写入、跨实例读取与现场核实。

开启 `--openviking` 时，共享后端保存每轮核对通过的事实和独立的服务 runbook。两端用不同身份，在各自的新会话中请求原生 Provider 查询同一演练目录。交班时对照实际读取的 URI 与内容哈希，再独立读取当前 HTTP 窗口。[运行和核对 OpenViking 交班](README.md#用-openviking-做跨实例交班)

稳定事实的修订单独观察。在 A 的环境迁移支付诊断入口，修复会话根据原生 Memory 查到旧入口并收到 410，再按回执查到可用的新入口。原生后台执行 `memory replace` 后，新会话只从核对过的 Memory 加载入口，首个工具调用应直接查到新入口。原始 Memory 和修复会话的文件分别留存，诊断查询走只读工具。

完成运行后，`http-workset.json` 把同一事故的初判快照、探测状态、分支和恢复证据归入一条 `working_only` 记录。回放只提供初判时采到的状态序列，查询超出已有回执时得到 `insufficient_capture`。学员可据此决定下一轮要采什么。[工作样本回放](README.md#回放一次已完成的事故初判)

开启 `--enterprise` 时，目标服务的实际 HTTP 请求经过上游依赖。故障中的告警、指标、日志和调用链冻结成只读快照，对侧独立的同名服务故障用于排除题。事故恢复回执与预先记录的故障计划一起支持独立标注。Hermes 在新会话中查询快照，第 19 讲评分器核对根因和实际引用。综合实战还为每个原事故派生两道题，分别用恢复前后的独立故障回执和显式覆盖缺口，检查同集群证据归属和证据不足时的判断。派生题沿用原事故分组，由独立版本的评分器验收。[运行和核对根因评测](README.md#把巡检事故做成根因评测题)

共享上游练习另起两套 HTTP 环境，开发题与留出题各有一次独立故障。每起事故用两个不同的 trace ID 追到同一个根服务，同期核对独立健康对照。一次获批处置后，验收全部服务的两个恢复窗口，再用冻结快照比较调查 Skill 对影响范围的判断。开发合格的版本才进入留出回放。[运行和核对共享上游练习](README.md#一个根故障影响两个下游)

同时开启 `--langfuse` 时，两端的巡检与分支调查由 Hermes 原生插件采集。取回 Trace 后，先核对本地 Session 和报告 Item，再把原有快照与独立标注接入数据集。按版本取回的题包可重新运行。发布数据集需显式执行单独的命令。[运行和核对 Langfuse 采集](README.md#把巡检与分支记录接入-langfuse)

开启 `--gepa` 时，第一轮以同一版种子 Skill 启动官方 GEPA 搜索。训练和验证使用冻结的 HTTP 回放题。显式开启 `--live` 时，训练反馈由官方提案器交给模型反思。有验证增益才锁定候选哈希，在发布验收题和最终留出题上分别成对回放。两组结果用于对照审计，正式发布仍由 SkillClaw 流程决定。[运行和核对 GEPA 对照](README.md#用-gepa-做一轮离线对照)

## 怎样验证 Skill 的一次进化

1. **先确定假设和评分口径。** 例如 A 漏掉了同一事故中的另一个受影响服务。写清应补到什么、允许查哪些范围、怎样识别把另一场事故误收进来。候选生成前冻结评分口径。
2. **按事故组分数据。** 现场归档用于 SkillClaw 蒸馏，`working_only` 用于回放复盘。GEPA 从单独冻结的训练题获取反馈，用验证题选候选。发布验收题检查可否采用 SkillClaw 候选，最终留出题用于独立审计。同一事故的相邻窗口、改写和派生快照留在同一组。
3. **固定条件成对回放。** 比较 Skill 时只换 Skill，固定模型、工具、预算、环境快照、记忆版本与初始上下文，每题开独立会话。另做一次固定 Skill 的记忆前后对照，验证入口修订。真实模型对照预先指定重复次数和判定方式，保留逐次结果。基础设施失败单独计数，恢复可比较性后再做决定。
4. **按预定门槛决定。** 候选至少修复一项预定业务失败，现行版通过的题不得回归，关键题必须全部通过。范围、证据、审批和恢复是硬门槛。达不到门槛就保留现行版。发布后审计失败则恢复上一个批准版本，并检查接收端。
5. **用下一轮任务验证采用。** A、B 新任务的真实工具选择、结果与结论都应能追到读取的 Skill 哈希。用旧版在同一快照上重跑代表题，检查行为变化是否来自方法更新。把两边新暴露的失败加入下一轮工作集。

评测集至少覆盖下面的行为。每类工作、验收或留出样本使用不同的事故组，按冻结的标注判分。

| 样本 | 独立标注与判定 |
| --- | --- |
| 单服务、证据齐全 | 已有的单告警调查仍能给出准确影响范围和根因，并引用实际取得的回执 |
| 多服务属于同一事故 | 报告补全所有已证实受影响服务，保留未确认项 |
| 同集群存在并发事故 | 影响范围、根因和引用都归到目标事故 |
| 跨集群存在相似症状 | 工具查询与报告证据都留在获准范围 |
| 关键证据缺失 | 报告保留未知，并写明需要补查的证据 |
| 恢复出现短暂抖动 | 单次 HTTP 200、样本不足和重复窗口都不能关闭事件，须有两个独立健康窗口 |

本机脚本模型用于验收消息、工具、存储、比较与分发接线。真实模型上的业务收益由有预算上限的成对实验决定。完整课程验收要保留 Langfuse、OpenViking、GEPA 和 SkillClaw 各自实际运行的回执。

## 模块验收与交付

| 模块 | 组件 | 验收出口 |
