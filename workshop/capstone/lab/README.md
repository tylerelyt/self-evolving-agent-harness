# 在业务现场逐步接入 On-call Agent

这四步逐项搭建本讲的双实例自进化系统。建议先按[运行双实例演练](../README.md#运行双实例演练)复现完整参考流程：本地 HTTP 服务实际运行，Hermes 默认使用脚本模型，第一轮处理故障并生成、评测、发布候选，第二轮交换故障类型，核对实际采用与回退条件。

工作台里的两套服务环境已经在接收请求。「概览」展示现场状态，「指标」「日志」「变更」提供调查材料，右侧的 SRE Agent 起初离线。你接下来要做的是把它带上线，再让它接手事故、用上历史经验，并在后续工作中改进方法。

业务工作台是同一套巡检与演化系统的操作和观察入口，持续对话用于复核业务证据。先按[启动说明](../README.md#启动本地工作台)打开工作台。从仓库根目录打开 Coding Agent，先让它读取本目录的 [AGENTS.md](AGENTS.md)。之后每次只给它一个需求。它会在同一份 [self_improvement_agent.py](self_improvement_agent.py) 中实现、自动检查并修正失败；你回业务页面使用刚接好的能力。

## 第 1 步，让 Agent 上线

先看正常现场：哪些服务有请求，最近一个窗口的错误率和延迟是多少，哪些服务的请求还不足以支持判断。然后把这一句交给 Coding Agent：

> 让 Agent 上线，持续巡检这两套服务环境。

等它检查通过，回工作台打开「练习与运行」，点击「启动 Agent」。服务的最近检查时间应持续更新。打开右侧的 SRE Agent，点击「新建对话」，问它：

> 现在有哪些异常？请分别检查两个环境。

读答复时，对照它引用的服务、指标窗口和工具结果。再追问一句：

> 哪些判断有足够证据，哪些还需要继续观察？

这两次提问应出现在同一段对话里。切到「指标」或「日志」后继续提问，已有上下文仍在。

## 第 2 步，让它接手告警

持续巡检在跑，但事故还需要调查、交接和后续恢复。给 Coding Agent 提出下一个需求：

> 让它接手监控告警，调查故障并把结论和恢复建议通知我。交接后继续巡检。

检查通过后，在「练习与运行」点击「应用代码」。这里将 A 的 `payments` 称为支付侧，将 B 的 `orders` 称为订单侧。先等正常巡检，再给支付侧注入持续失败，给订单侧注入间歇失败。故障开关由环境控制，告警由外部监控发出。

回到「概览」打开这两起事故。你可以点击「交给 Agent 调查」，也可以在 SRE Agent 中说：

> 核对这两起告警的初判和补查记录，说明影响、证据、还不能确认的原因和恢复建议。

告警接手、初判和补查由持续巡检主链推进。对话中的附加复核帮助解释这些记录。观察工具调用和结果，再追问：

> 这两起事故能用同一种处置方式吗？哪些结论只是当前探测说明的现象？

对照业务指标、请求日志和变更记录，判断建议是否有依据。需要回看原始执行时，再打开「执行证据」。确认交接后，继续观察服务检查时间是否推进。

读过恢复建议，在「概览」的已交接事故上点击「申请恢复」，核对「批准恢复」对话框中的事故、环境、服务和调查报告，再点「批准并执行本地恢复」。页面先显示「恢复验证中」，后续巡检取得两个互不重叠的健康窗口后才确认恢复，再进入下一步。

## 第 3 步，让新任务用上历史经验

刚才的对话还记得事故，不等于下一段新对话也能查到它。给 Coding Agent 提出这个需求：

> 让它记住已经处理的事故，在新的任务里按需检索，并重新确认当前状态。

检查通过后应用代码。到「Memory」点击「复盘已恢复事故」，查看复盘结果。没有保存新事实时，先读记录中保留原状的原因；有了事实后，再核对其来源。你可以点击「查看原始事故」，对照当时的调查与恢复记录；「新会话召回」会单独检查一次检索和现场取数。

然后在 SRE Agent 点击「新建对话」，问：

> 刚才支付服务发生过什么？请查历史记录，再核对它现在的状态。

核对两件事：历史结论引用的是哪次事故，当前判断取得了什么新证据。继续追问这份经验是否适用于另一套环境。查不到、范围不符或现场已变化时，答复应保留这些限制。

再切到「入口与 Memory 修订」，按顺序读取旧记忆、迁移本地入口、实际排查、后台修订、新会话验证。每步结束后停下来核对：入口迁移不等于 Memory 已修订，写入完成也不等于新任务已经采用。这里的受控环境与分步执行器由工作台提供，原生 Memory 的读取、`replace` 和新会话工具回执才是观察依据。

## 第 4 步，让团队改进下一次的做法

Memory 留下了发生过什么，Skill 则决定下一次怎样调查。最后给 Coding Agent 提出这个需求：

> 让团队从事故经历中改进 Skill。只有独立评测证明更好时才发布，再用下一起事故验证实际采用。

检查通过后应用代码。在两端分别完成故障调查和恢复，再到「Skill 学习」查看原始初判会话形成的演化批次。补查分支保留给处置与复盘；独立评测使用冻结的持续失败、间歇失败、首次成功未复现三个现场，对新旧 Skill 从新会话开始成对回放。核对候选、逐题结果和发布决定。你可以在 SRE Agent 里问：

> 这次准备改什么？哪些评测结果支持发布，还有哪些证据没齐？

有了发布记录，再制造一组新的故障。可以交换两端的持续失败与间歇失败。观察新的调查是否多做了获准的复核，再核对实际使用的 Skill 版本。两端都有新的采用证据，才能确认共享方法已经进入后续工作。

四步完成后，先对当前实现重跑累计检查，再将同一份实现交给[完整双实例演练](../README.md#运行双实例演练)：

```bash
.deps/hermes-agent/.venv/bin/python -B workshop/capstone/lab/check.py --stage 4 \
  --out workshop/capstone/runtime/final-check
.deps/hermes-agent/.venv/bin/python -B workshop/capstone/self_improvement_agent.py \
  --implementation workshop/capstone/lab/self_improvement_agent.py \
  --stage-check workshop/capstone/runtime/final-check/check.json \
  --out workshop/capstone/runtime/own-fleet --verify-closed-loop
```

这两条命令默认使用脚本模型；真实模型验收时，两条都加 `--live`。每次重跑使用新的输出目录。最终演练会冻结这份实现，核对累计检查的源码摘要与运行模式，并实际调用六个实现入口；不需要另写一套总编排。`report.json` 的 `implementation` 保存源码摘要、累计检查摘要与实际调用记录，`closed_loop_verified` 为真才证明本轮完成发布及后续采用。候选未通过、没有增益或采用证据不足时，保留正式版并继续巡检，但完整提升链路仍未验证；严格验收返回非零。SRE 对话结束或单次调查完成，不能代替这些证据。

在工作台「正式版本回退」准备方案，核对当前版本、目标版本与两端范围，再明确批准。回退后分别检查真实 HTTP 新任务与冻结现场的行为回放；前者证明当前接收和执行，后者在相同失败现场比较方法。两种来源不能混称为线上验证。生产灰度和分布式平台的后续系统设计见[设计练习](../PRODUCTION-DESIGN.md)。

如果只完成一端事故，后台会继续等另一份合格经历；候选没有改进或出现回归时，应保留现行版。发布后还没有新任务时，应显示等待采用验证。这些结果都可以继续追问，并回到原始记录核对。

## 实现与检查在哪里

日常使用从业务页面和对话开始。「练习与运行」保留本步需求、实现进度、检查记录、故障注入和恢复申请。Coding Agent 自动运行的检查也会回到这里，绑定这次实际使用的代码内容；修改后需要重新检查、应用，再看现场行为。

四步都使用当前目录的 `self_improvement_agent.py`。希望拆开看实现时，可以对照以下入口：

| 需求 | 实现入口 | 主要核对内容 |
| --- | --- | --- |
| 持续巡检 | `patrol_config` | 服务范围、抽查数量、间隔与持续检查点 |
| 告警调查与交接 | `route_alert`、`branch_report`、`notify_operator` | 同回合接单、从报告分支、真实通知与继续巡检 |
| 新任务检索历史 | `recall_memory` | 有来源的事故事实、新会话和当前 HTTP 证据 |
| 评测后发布 | `release_policy` | 两版证据可比、候选无回归且有严格增益 |

通常由 Coding Agent 运行检查。需要单独重跑时，从仓库根目录执行：

```bash
.deps/hermes-agent/.venv/bin/python -B workshop/capstone/lab/check.py --stage 2 \
  --workbench workshop/capstone/runtime/workbench --live
```

`--workbench` 使用终端打印的实际 `Workbench state`，替换示例中的路径；通过 `--new-state` 启动时，该路径包含本次演练的独立后缀。退出后可用同一启动命令创建新演练，旧证据仍在原目录。默认工作台使用真实模型，检查带 `--live`；显式以 `app.py --offline` 检查接线时，检查命令不加 `--live`。离线模式保留真实工具和会话记录，模型答复由本机脚本生成。

检查支持 `--implementation` 指定实现文件、`--out` 指定独立的新输出目录。第 3、4 步会实际等待恢复窗口，耗时比前两步更长。检查通过、代码已经应用、现场行为已出现，需要分别核对。

命令行参考实现、数据集、离线优化和发布恢复说明见[综合实战配套工程](../README.md#完整参考运行)。
