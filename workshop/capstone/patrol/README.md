# 巡检与检查点

本模块在四个本地 HTTP 服务上运行持续巡检，并保存可恢复、可分支的原生 Hermes 执行记录。启动与故障注入步骤见[巡检实作](LAB.md)，告警接管与补查见[On-call 实作](ONCALL.md)。本目录的 Python 入口委托到 `apps/oncall/patrol/` 中的维护实现。

## 运行组件

| 组件 | 职责 |
| --- | --- |
| `environment.py` | 启动订单、支付、库存和通知服务，产生真实 HTTP 流量与观测窗口；故障注入后由环境监控发出告警 |
| `patrol.py` | 按服务队列抽样调度，启动 Hermes Turn，核对工具回执和报告，提交巡检记录与检查点 |
| `hermes_runtime.py` | 注册只读工具，管理原生 SessionDB，按已提交的报告 Item 恢复或 fork 会话 |
| `investigation.py` | 从事故报告 fork 补查，获取三次新探测，形成调查结论和恢复建议 |

外层调度决定何时启动下一项巡检、轮到哪个服务；Hermes 的工具循环在单次任务内完成取数、按需检索和报告。默认每轮抽查两个服务，轮次之间等待指定间隔。

## 观测与判断

每项巡检通过 `service_snapshot` 读取实际请求形成的当前窗口。`service-patrol` Skill 规定实验口径：请求少于 10 个时记为 `insufficient`；样本足够时，5xx 比例达到 5% 或 P95 达到 500ms 记为 `abnormal`，其余为 `healthy`。读取失败记为 `unavailable`。

通知服务流量较低，零错误率仍可能对应样本不足。清除故障后，旧失败请求也会在滚动窗口中保留一段时间。判断需同时核对窗口、样本量和实际回执。

`search_inspections` 只检索相同服务与环境的已提交巡检记录。历史观测可用于比较变化，当前健康状态由本次 HTTP 窗口决定。持续应用接入 OpenViking 的历史事实与 runbook 检索另见[记忆参考](../../../apps/oncall/MEMORY.md)。

## 持久化证据

每项巡检提交服务范围、观测窗口、请求数、5xx 比例、延迟、判断和实际引用的历史记录。`patrol.sqlite` 保存巡检历史、服务检查点与事故记录；同一状态目录下的 `hermes/state.db` 保存原始 Hermes 会话。

检查点包括 Session、巡检回合编号和报告 Item。Harness 从运行时读回工具回执与报告并核对后，才在同一事务内写入巡检记录、更新检查点。未提交的回合不替代上一个可核查位置。

例行巡检复用对应服务的 Session，追加新的 Turn。`resume` 从已保存的检查点读回原始观测与报告；`fork` 按已提交报告 Item 截取会话前缀，创建具有独立 Item ID 的子 Session，并保留父会话关系。分支调查的新增探测与原巡检证据分别保存。

## 告警与后续学习

环境监控产生带事故 ID 的原始告警，Harness 核对服务与环境后，通过原生 `steer` 将事件交给当前巡检回合。Agent 读取 `oncall-alert-triage` Skill 完成初判；长调查再从报告 Item fork，重新取证并向值班工程师交接。处置由外部批准与状态机控制，恢复由后续巡检验证。

这些记录既是后续调查的历史，也可按事故导出为回放材料。原始 Session/Item 与观测范围为复盘和独立评测提供证据；候选方法是否改善判断，仍需在固定样本上比较。双实例归档、SkillClaw 演化、发布与采用的完整入口见[综合实战](../README.md)。
