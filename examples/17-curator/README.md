# 第 17 讲：整理诊断技能库

本讲练习连接池与连接泄漏诊断技能的生命周期管理：自动标记陈旧、归档退役技能，让原生 Curator 判断是否需要整理，再检查应急手册、支持文件和诊断能力是否保留。

## 本讲独立练习

四项起始技能都在本目录中，无需先运行技能创建或增量修订。先用活动时间触发状态转换，核对应急技能的 `pin` 保护，再观察模型如何组织两个重叠入口。最后分别检查归档恢复和快照回滚。

先交付 `transitions.json` 与 `recovery.json`，解释一次归档和一次内容恢复的差别。整理前后，分别用相同容量压力与疑似泄漏任务开启独立会话，对照 `comparison-capacity.json`、`comparison-leak.json` 和原始工具回执。保留原生整理回执、主文件及支持文件差异，确认专用诊断规则和实际任务能力都没有丢失。

先在仓库根目录按根 README 准备固定版本的 Hermes 依赖，再进入本目录：

```bash
cd examples/17-curator
bash run.sh --offline  # 验收负例、原生状态转换、保护和恢复，不调用模型
bash run.sh            # 整理前两项诊断 → GLM 整理 → 整理后同题诊断
```

也可使用固定依赖环境打开 [workshop.ipynb](workshop.ipynb)，逐格运行。没有设置 `GLM_API_KEY` 时会隐藏询问；默认连接智谱官方接口。`GLM_BASE_URL` 可显式指定兼容端点，例如本地预算代理，代理令牌仍经 `GLM_API_KEY` 传入，不写入文件。

每次运行新建 `runtime/curator-*`，终端会给出 `REPORT.md` 路径。查看状态转换、原生整理回执、两项诊断结果以及恢复记录。终端按 `Ctrl-C` 停止，Notebook 使用“中断内核”；本练习不启动常驻服务，重新练习时重启内核。会话与数据库在结束或异常时关闭。`runtime/` 和日志不纳入版本管理。

## 课后练习

Oncall 技能库里有重复或相近的排障流程，也有长期未使用的旧技能。在不逐条人工清理的前提下，设计自动状态管理、语义整理与内置技能修剪的协作过程；说明如何让模型判断分组、保留公共入口和特殊资源，并验证整理后的任务仍然能完成。应急手册如何保护？支持文件或脚本失联时怎样发现和恢复？

本例使用四项**构造教学技能**，不含生产事故或真实应急步骤：

| 技能 | 练习动作 | 应观察的结果 |
| --- | --- | --- |
| `connection-pool-triage` | 检查连接池指标与容量压力 | 保留可发现的诊断入口 |
| `connection-leak-investigation` | 检查连接释放路径 | 特殊检查不因合并而丢失 |
| `disaster-recovery` | 标记 pinned，再执行自动管理和整理 | 不被归档或修改 |
| `retired-db-debug` | 设置为长期未使用 | 原生归档后可以单独恢复 |

[materials/](materials/) 提供全部初始文件。先运行 `apply_automatic_transitions`，再运行 `run_curator_review(consolidate=True, synchronous=True)`。状态转换不需要模型；语义整理使用 GLM。配置同时开启 `prune_builtins`，但这四项都是课程创建的技能，不能拿本例声称已验证内置技能修剪。

整理可以发生合并，也可以保持原样。`no-op` 只有在原生运行完整结束且文件未变时才成立，报错或中断不能算作 no-op。不要以文件减少数量判断成功：让 Agent 在整理前后完成同样的两项诊断，再演练“单项恢复”和“快照回滚”的区别。

## 同题检查诊断能力

每项任务只给集群、服务和窗口，现场数据由只读 `diagnostic_query` 返回。Agent 自行发现入口、读取相关规则，再按参数查询指标、连接持有记录，以及释放代码是否已采集。两项任务使用相同输出接口：诊断、三个必要判断、实际证据编号和结构化下一步。

容量题需要核对峰值需求与连接上限、负载回落后的归还情况，再提出容量和慢查询检查及结果验证。泄漏题需要结合负载已恢复、连接仍被持有和异常请求的记录；释放代码尚未采集，因此只能报告疑似泄漏。下一步须覆盖正常、异常和提前返回分支，并说明怎样用成功/失败请求验证归还、active 和 waiting 的恢复。返回正确分类、随便读取一份文件或写“继续检查”，均不足以通过。

支持资料包含可核对的结构化诊断规则。整理可以重命名、迁移参考文件，或把规则合入共同入口；检查不绑定原文件路径。需要保留的是规则的完整条件、专用检查与验证计划，以及 Agent 真的读取规则、取得本题回执并据此回答的证据。主文件引用仍由独立的可达性检查核对。

支持文件失联演练选择实际仍被引用的资源。若整理已将全部细节内联，恢复演练先回到原始快照再制造资源缺失，并在 `recovery.json` 单独记录准备步骤；不会把合法内联判成整理失败。此步骤位于同题能力检查之后。

整理前后的模型、题面和快照固定，使用不同 Session 与数据库，原始消息分别保存在 `probe-before-*.json`、`probe-after-*.json` 和各自的 SessionDB。对照报告逐项比较能力检查；基线失败或输入不同不能宣称能力保留。完整运行增加到四项诊断任务，每项最多 12 轮，另有 Curator 调用；这些上限不等于费用上限。

## 实现与边界

[curation_workshop.py](curation_workshop.py) 直接调用原生 `skill_manage`、状态转换、Curator 和快照恢复；[curator_read_adapter.py](curator_read_adapter.py) 是课程适配层，传递真实读取记录，并额外要求归档合并前读过目标包的全部当前文件。工具白名单也是课程限制，不是 Hermes 原生隔离沙箱。这里没有自动采用生产技能目录。

验收看生命周期、应急文件、引用完整性、整理前后同题能力与恢复结果。[diagnostics.py](diagnostics.py) 核对相关规则、现场回执、判断、引用和可验证下一步；[test_risks.py](test_risks.py) 包含错误资料、缺查询、跨范围回执、虚构确认和遗漏异常分支等负例。诊断内容与纯 JSON 格式分列；唯一 JSON 代码块可以提取，块外解释、多个块或歧义不自动通过。机器检查的是结构化结论和计划，不表示已经执行释放路径验证；自由解释是否充分仍须人工阅读。

离线通过只证明固定负例、原生生命周期和恢复机制。真实模型能否完成整理、找到迁移后的规则并保持诊断能力，须以新的完整模型运行及两份同题对照为准；一次通过也不证明统计收益或生产泛化。
