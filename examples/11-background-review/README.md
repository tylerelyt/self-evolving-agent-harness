# 第 11 讲：后台复盘

## 面试题

假设你负责一个在线值班助手。它处理完请求后，用户常会补充一些今后仍适用的要求，例如报告要先给结论、暂时无法确认的原因要明确说明。团队希望助手以后能记住这些要求，但整理经验可能还要调用一次模型，用户不能每次都等它整理完才能继续工作。

你会怎样安排任务结束后的经验整理？希望正常请求及时返回，整理过程可以追查；整理没完成或没留下内容时，也不能把它报告成已经学会。追问，你会怎样验证整理确实在后台执行，以及哪些情况下不应该启动？

### 参考答案

我会先把用户等待的结果和后续经验整理分开。前台已经完成的工作应该及时返回；整理还需要额外调用模型，也可能没有值得保存的内容。要是前台一直等它结束，就会把整理的耗时和失败带到正常请求里。因此我会让 Harness 在本轮收尾时检查是否需要安排复盘，把当时的会话副本交给独立的后台实例，再把控制权交回用户。

副本要包括用户要求、工具结果和纠正过程，只给最后一句回答往往看不出经验从哪里来。后台使用自己的对话，后续用户消息不会自动追加到这份副本，复盘对话也不写回前台。它的工具范围应限制在经验管理所需的能力内，让后台围绕刚完成的任务整理经验，前台继续响应用户。

触发和保存也要分开判断。程序按配置间隔和本轮结束状态决定要不要安排检查，后台模型再判断什么值得留下。检查开关都关闭，或者本轮确实被中断，就不应该启动这次自动复盘。即使后台启动了，也可能认为已有等价内容，不再写入，不能要求每轮都制造一条新经验。

验证时我会记录前台返回、后台启动和结束的时间，核对线程是否在前台返回以后仍然运行。然后分别看工具调用及回执、文件前后变化和失败原因。线程结束、工具成功和文件变化要分别核对，才能还原这次复盘到底做了什么。守护线程的生命周期跟随服务进程，进程退出前还要记录是否有尚未完成的复盘。

本练习沿这条链路观察一次偏好保存，再对照关闭自动检查和实际中断两种情况。输入明确要求记住偏好，前台也可能先保存；因此要把前台操作与后台新增操作分开核对。到第12讲，再运行新的调查会话，观察积累的经验怎样参与下一次行动。

## 练习与核心代码

本练习使用仓库现有的 `AIAgent` 实现观察异步复盘。前台完成后即可返回，后台继续整理；复盘使用 `daemon` 线程，退出进程前应先查看后台是否已经结束。

运行入口是 [run.sh](run.sh)，主要观察代码在 [run_background_review.py](run_background_review.py)。**这几行是核心**：`messages_snapshot` 的记录核对后台拿到了什么；`agent.run_conversation(...)` 返回后记录前台时点；`rt.join(timeout=60)` 后检查 `rt.is_alive()`，区分仍在运行与结束；`review_tool_results(events)` 排除前台旧回执，再与 `snapshot_memory()` 的前后内容对照。`join()` 是练习观察者等待后台，前台响应流程没有等待它。

## 观察什么

- 触发请求与实际线程启动分别记录，前台返回时后台是否存活按实际结果报告。
- `join(timeout=60)` 后检查 `is_alive()`：仍在运行与线程结束分别报告。线程结束不等于工具成功，工具成功也不等于本次文件发生变化。
- 工具请求及回执、失败原因、前台返回时与当前观察时点的记忆文件，保存到 `output/review_trace.json`。该文件包含本练习输入，使用教学数据即可。
- 本练习观察两个阻止触发的条件：Memory 和 Skill 自动检查同时关闭；本轮实际被中断。Memory 间隔为 0 只关闭 Memory 自动检查，Skill 条件满足仍能触发。

## 机制与范围

`agent/turn_finalizer.py` 检查最终回答、未中断以及 Memory/Skill 任一检查标记。计数在 `agent/turn_context.py`；后台工作在 `agent/background_review.py`，另建 `AIAgent`，限制执行工具，不把复盘对话写回前台。

脚本在本进程内包装后台工作函数和 `run_conversation` 以观察输入、返回和线程状态，不改框架源码。工具回执、文件变化与警告异常分别保存。若后台仍在运行，脚本记录中间状态并停止后续对照，保持本次复盘与后续任务的归属清楚；退出进程可能中止该线程。

本练习隔离使用 `.hermes-home/`，前台提示明确要求记住偏好，因此前台也可能先调用记忆工具。后台不再写入可能是已有等价记忆，不能直接判断模型漏记。要观察不带明确记忆要求的自主复盘，应另按正文观察题安排任务。

## 运行

前置：先执行仓库 `scripts/setup_deps.sh`，再用 `scripts/setup_deps.sh --check` 核对固定 Hermes 提交及环境，并准备模型凭证。`run.sh` 使用 `.deps/hermes-agent/.venv` 的解释器，与前 9 讲的 Notebook 环境分开；不要直接换成 Notebook 的解释器。脚本沿用进程代理设置；需要直连时在调用前清空代理变量。

```bash
GLM_API_KEY=你的智谱key bash run.sh
```

输出到 `output/run.log`。结合前台返回、后台启动和结束的时间，核对复盘怎样与前台并行。若复盘很快结束，前台返回时可能已观察不到存活线程，仍可从启动与结束记录还原过程。
